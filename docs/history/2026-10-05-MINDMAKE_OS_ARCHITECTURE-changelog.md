The 2026-08-19 work made Vera's feedback loop run end to end for the first time. Watching the first real lap showed it did not finish one: it wrote corrections but never finished consuming what it read, so the same clusters would have returned every Sunday forever.

- **Provenance stops coming from the model.** `consumed_feedback_ids` was whatever Sonnet echoed back. Asked to reproduce UUIDs for clusters covering 191 rows inside a 4000-token budget, it returned a 50-id sample and dropped 2 of 10 clusters outright. Ids, agent and reason code now join from the clusterer's own output on `cluster_key`; a `cluster_key` the clusterer never emitted is dropped rather than written as a correction with no traceable evidence. The model is no longer asked for ids at all, which also stops the prompt shipping 191 UUIDs it cannot use.
- **And the fan-out stops reading one item.** `Fan out feedback ids` used `$input.first().json` while `Write Corrections` runs once per correction, so with 8 corrections it fanned out only the first. Between the two bugs, 10 of 187 eligible rows were ever marked consumed. Data repaired alongside the code: the 8 pending corrections were backfilled to true membership (187 ids) and those rows consumed. A verification run then found the 2 clusters the model had dropped and consumed all 4 of their rows. The next scheduled run sees no duplicates.
- **A new class of silent failure: the unpublished draft.** n8n Cloud keeps a draft and a published version, and an edit made through the MCP `update_workflow` tool writes the **draft**. A manual test run executes the draft and passes while the cron keeps running the old published version, so a fix looks shipped and is not. Vera's provenance fix passed a manual run while Sunday would still have executed the broken code. Nothing in the OS could see this: the workflow does not error, its heartbeat is written, its counts look healthy. `fleet-reconcile` now compares `versionId` against `activeVersionId` (both already on the workflows list it fetches, so no extra API calls) and raises its own tier-2 `silent_failure`; `workflow_health.unpublished_draft` carries it. - **The repo copies stopped lying.** The checked-in Vera JSON declared `credentials.httpHeaderAuth` with no `authentication` parameter while live used `predefinedCredentialType`/`supabaseApi`. - **One earlier claim in this document was false.** The 2026-08-19 entry said two classifier bugs were "caught by unit tests". ### 2026-08-19 (later): the OS stops grading its own homework, the backlog starts ageing out, and the feedback loop closes for the first time

Krish asked three things: stop the news randomly drying up, archive what he does not action so he only ever sees fresh material, and make his standards actually compound. The design for all three already existed. Two of the three had never once run.

**The structural fault, common to all three.** Every health signal in this OS is self-reported by the workflow that is supposed to be healthy, and heartbeats are written at the END of a run. A workflow that dies at node 3 writes nothing, and nothing is indistinguishable from "not scheduled today". So the failure mode that actually happens is exactly the one the monitoring cannot see. `credential_health` held 20 rows, all `healthy`, last verified 2026-05-19, while three workflows failed on credential errors every day for three months. The sensor was unplugged and stuck on green.

- **New external observer.** `api/health/fleet-reconcile.ts` (Vercel cron, every 6h) reads the **n8n executions API** and writes `workflow_health` + `fleet_failures`. Deliberately a Vercel cron and not an n8n workflow: an n8n workflow monitoring n8n shares the blind spot it exists to close. There is already a `Truth Reconciler` workflow with a `Fetch Live Workflows` node that was meant to do this; it has failed 2/2 on an expression error, so the fix itself was broken. Failures are grouped by cause (`credential | quota | logic | network`), so a credential outage is one story rather than six unrelated alerts. First run over live data: **10 dead, 6 degraded, 1 failing** out of 121 workflows, 108 failed runs traced to three broken credentials and 26 to two blown quotas.
- **Two classifier bugs caught before deploy.** n8n wraps almost every non-2xx in "Forbidden - perhaps check your credentials?", and puts the actionable cause in `error.description`, not `error.message`. Classifying on the message alone made Zara's "Monthly usage hard limit exceeded" and the Orchestrator's Google Drive rate limit both read as broken credentials, which would have sent someone rotating perfectly good keys. Quota is now tested before credential, and `description` feeds both the stored message and the classification. These were caught by inspection, not by tests: despite an earlier note here saying otherwise, no test covered them until `scripts/check-fleet-classifier.mts` was added on 2026-08-24 (CI). Separately, `degraded` now alerts at tier 2: Zara errors on only 38% of runs yet has written no `zara_signals` row since 2026-07-24, and silence at 38% is how that stayed invisible.
- **Three workflows repaired.** `HARO Ingestion` had failed **94 of 94** runs against Gmail credential `AFgF8OOuBhYHbiyo`, which no longer exists; rebound to the mailbox the Inspiration Sweep reads successfully every morning. `Vera Feedback Aggregation` was bound to a generic `httpHeaderAuth` credential that sends no `x-api-key`, so it 401'd 2/2. `Maya Customer Acquisition Sweeper` (12/12, "Credentials not found") and the two quota failures are surfaced but left for Krish: one is a plan decision, not a code fix.

**(b) The backlog could not age out, and archiving destroyed the evidence.** The Monday purge exempts drafting/review/approved/published from expiry deletion so started work is never hard-deleted. The gap: an idea promoted out of `seeded` and then abandoned was immortal. 160 live rows, 80 already past `expires_at`; `drafting` 48 of 49 expired (avg 31 days), `review` 9 of 9 expired (avg 70 days, oldest 74).

- **`updated_at` could not detect any of it.** Background re-scoring sweeps touch rows constantly, so those 74-day-old review items reported "touched 8 days ago" and *zero* rows looked idle. New `content_ideas.state_changed_at`, moved by a trigger only on a real state transition, measures decision progress instead of row activity.
- **`archive_stale_content_ideas(days, dry_run)`** buries anything whose state has not moved in 14 days (`system_config.content_staleness_archive_days`), exempting rows linked to a shift, graduated to the library, or published. Run once at 14 days: **53 rows archived**, including all 9 stale `review` items. Everything left past the threshold is shift-linked, i.e. work Krish committed to. Daily at 10:00 UTC via `api/content-ideas/archive-stale.ts`.
- **Archive now means archive, not forget.** `api/shifts/detect.ts` filtered `.is('buried_at', null)`, so hiding a row also deleted it from the trend corpus and "keep reading trends from it" was impossible by construction. Stale-archived rows (`buried_reason` prefixed `stale:`) are re-admitted; rows buried for any other reason stay out, and dedupe burials especially, since their citations already live in their keeper's `meta.recurrences` and would double-count.

**(c) The standard is good. The learning loop had never closed, not once.** Generation-time enforcement is real and working: five active pillars with 6-8 anti-patterns and 3-5 required evidence types each, injected with the voice rules, the CLO-020 bar, temporal class, and `newsletter_source_yield` as a source track record.
