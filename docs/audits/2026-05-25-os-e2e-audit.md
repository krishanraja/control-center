## Section A — Critical bugs (P0, fix this week)

### A1. Marcus Daily Brief: Telegram push fails on every cron run

- **Workflow:** `d2sHSeyXMmu8Xe0C` "Marcus | Daily Brief 06:30"
- **Symptom:** Every 06:30 UTC cron run for the last 2+ days has errored.
- **Root cause (from execution `8456` data):** the `Telegram push` node POSTs to `chat_id: '5712840770'`. Telegram returns `400 Bad Request: chat not found`.
- **What works:** All upstream nodes (Fetch live data → Pull live data → Sonnet brief → Parse + stamp → Write home_intelligence) succeed. **home_intelligence.daily_brief and top_three DO get refreshed daily.** The brief Krish has on Home right now ("Get the SuperAI Singapore proposal drafted and submitted...") was generated TODAY at 10:30 UTC, not stale.
- **What's missing:** Krish has not received the daily Telegram brief in at least 2 days.
- **Note:** the `n8n/workflows/*.json` snapshot of this workflow has `chat_id: '6773796504'`, but the live workflow has `5712840770`. **The snapshot and the live version diverged.** One of those two IDs is the right one and someone must reconcile.
- **Fix effort:** 5 minutes. Update the `Telegram push` node `jsonBody` `chat_id`.

### A2. Self-healing tier workers all 401: Service Role credential never applied

- **Workflows affected (confirmed):**
  - `F6srw1yE9uH67q14` "System | Mindmaker OS | Silent Success Detector" — failing every 4h since at least 2026-05-22
  - **Almost certainly also:** `SXdHes0WwIovjPAB` "System | Critical Infrastructure Monitor" and `5fm6HXpMSQMjn0GJ` "Vera | Failure Pattern Sweep" (same node pattern)
- **Symptom:** `silent_failures` table has zero rows added since 2026-05-22 11:34 UTC. All 6 existing entries are from one batch of tier-4 critical_infra_down detections, all resolved within 19 seconds. **The system that's supposed to detect silent failures has been silent for 3+ days.**
- **Root cause (from execution `8688` data):** the `Audit Silent Failures` HTTP Request node has a `httpHeaderAuth` credential `nd473D3tq83O5PKP` ("Supabase Service Role") attached, **but** the node parameters set `authentication: "none"`. So the credential is dormant; PostgREST returns `401 No API key found in request`.
- **Tier-by-tier status:** Tier 2 (Silent Success Detector, every 4h) DEAD. Tier 3 (Critical Infrastructure Monitor, every 5m) presumably also DEAD with same bug — needs verification. Tier 4 (Vera Failure Pattern Sweep, Sunday 07:00) likely also DEAD — last successful Sunday is unknowable until inspected. **Tier 1 (in-workflow completeness contracts) is the only working tier, and only covers 8% of workflows (see D2).**
- **Fix effort:** ~15 minutes per workflow. Change `authentication` field from `"none"` to `"predefinedCredentialType"` and set `nodeCredentialType: "httpHeaderAuth"`. The credential is already correctly attached.

### A3. Agatha Lead Deep Enrich: Brave Search 422 — query shape bug + accept-header bug

- **Workflow:** `YPKjTnB2P6mqe4kG` "Agatha | Lead Deep Enrich"
- **Symptom:** every webhook hit from `/api/leads/:id/enrich` errors at the Brave Search node. 4 failed executions today (10:17, 10:19, 10:30, 10:32 UTC).
- **Root cause (from execution `8460` data):**
  - The `Brave Search` URL expression: `{{ encodeURIComponent(($json[0].full_name || '') + ' ' + ($json[0].company || '') + ' role LinkedIn') }}`. But the preceding `Fetch Lead` node returns a single object, accessible as `$json.full_name`, NOT `$json[0].full_name`. **`$json[0]` is undefined**, the query becomes the literal string ` role LinkedIn`, and after encoding/trimming Brave sees `q=` (empty).
  - **Bug 2:** the `accept` header is the long n8n default (`application/json,text/html,application/xhtml+xml,...`). Brave validates `accept` with an enum that only accepts `application/json` or `*/*`. **The prior audit (PR #70) claimed this was fixed.** It isn't.
- **The prior audit's CHANGELOG** at `n8n/workflows/README.md` claims SIX bugs were fixed on this workflow during the 2026-05-25 audit verification round. **At least 2 of those 6 (Brave URL shape, Brave Accept header) are still live.** I did not validate the other 4 (Brave token rotation, Sonnet credential, jsonBody shape, Parse Sonnet shape) — but if 2 of 6 regressed, all 6 should be re-verified.
- **Fix effort:** ~15 minutes. Two expression edits.

### A4. Kai Dependency Mapper: failing every 4h

- **Workflow:** `fBgBwoAg0YdkabtU` "Kai | Mindmaker OS | Dependency Mapper + Credential Health"
- **Symptom:** Failed at 00:00, 04:00, 08:00, 12:00, 16:00 UTC today — every 4-hour cron tick, all long-duration errors (~30-90s per attempt). Consequence: `credential_health` is 5 days stale (last update 2026-05-20). If a credential expires, you don't get the heads-up.

- **Fix effort:** Investigation + likely 30 minutes patch.

## Section G — Structural concerns (flag, don't patch)

### G1. The self-healing system has a single-config blast radius

Three independent tier workers (Silent Success Detector, Critical Infrastructure Monitor, Vera Failure Pattern Sweep) all hit the same authentication bug. One configuration mistake takes the entire layer offline, and **there's no meta-watcher** that catches "the watcher is dead". This pattern repeats: anything in the OS that's "the system that detects X" has no system that detects when X-detection breaks.

**Recommendation:** add a 5-minute meta-heartbeat workflow that:
- Queries each tier worker's most recent successful execution time
- If Tier 2 silent > 5h, Tier 3 silent > 10m, Tier 4 silent > 8d → Telegram Krish directly
- Writes its own heartbeat to a dedicated `meta_heartbeat` row in `system_health` so Kai notices if THIS breaks

Bigger work than this audit's "tighten" scope. Flagged.

### G2. Documentation drift is institutional, not local

`§4` of the architecture doc claims schemas that don't match reality on **7 tables and 1 view**. This isn't a single stale section; it's the result of code-changing-faster-than-doc with no enforced reconciliation. Stream 1's Day 1 work added the closure-architecture section but didn't reconcile the pre-existing drift.

**Recommendation:** a one-shot generator that regenerates §4 from `information_schema.columns` rather than hand-writing it. The doc remains hand-written above §4 (the strategic stuff that schemas can't infer), but the schema reference becomes machine-generated. Larger work; flagged.

### G3. Workflow naming convention has 3+ formats coexisting

`Agent | Mindmaker OS | Verb` (current new standard)
`Agent | Verb` (newer flat)
`OS — Agent Verb` (older, with proper em-dash)
`OS - Agent Verb` (older, with mojibake-likely hyphen)
`OS � Agent Verb` (broken mojibake)

The Status Board API and Kai both want to group by agent. They can't. **Lock the convention, rename the strays.** ~30 min of careful UPDATE in N8N. Some risk because IDs in workflow_runs reference workflow_id (which is stable) but workflow_name (which is what users see) needs renaming.

### G4. There's no surface that pushes radical action

The OS has 14 agents that REPORT (Marcus, Vera, Leo, Priya, etc.), 5 agents that ACT (Cleo, Nell, Nova, Felix, Maya) when triggered, 1 agent that ROUTES (Agatha). **There is no agent whose job is to PROPOSE.** No "Speculator" agent that watches MRR + pipeline + market signals + customer voice and authors weekly: "place this bet, here's the falsifiable hypothesis, here's the time-box, here's the est_mrr_impact." Marcus comes closest with `one_bet` but as noted in E2 his output is a rephrasing of the urgent queue, not a new wager.

The "$20K/month inside 60 days" outcome (O-2) requires acquisition velocity that doesn't currently exist anywhere in the queue. Without a propose-surface, you remain the only proposer.

**Recommendation (out of scope for this audit, but flagged):** add a `Speculator` agent that runs Sundays after Vera Feedback Aggregation, reads the last week's signals + bets + revenue, writes 1-3 proposed bets into `bets WHERE status='proposed'`, with reasoning. They surface in a new "Next Bet" Home card. Krish accepts/rejects/edits. Same mechanism as guests but for bets.
